## Bối cảnh

- Sheet thật của chủ repo: `DataThuChi_CaNhan`, tab `Transactions`, cột `id,date,type,source,category,amount,note` (chưa có `targetSource`). Ngày trong Sheet là UTC (`2026-10-26T17:00:00.000Z` = 27/10 giờ VN). Cột ngày của script cũ nên được chủ repo đặt định dạng `dd/mm/yyyy` bằng tay trong Sheet (script v2 tự đặt).
- **Apps Script thật của chủ repo** (chủ repo gửi ngày 28/10/2026) được giữ nguyên văn ở `tests/gas/fixtures/user-script.gs`; test e2e chạy đúng script này trong sandbox. Đặc điểm cần nhớ:
    - `doGet` trả mảng giao dịch (7 cột, ngày ra dạng ISO UTC); `?action=save&data=<json>` ghi bằng GET (cách duy nhất từng chạy thật trên trình duyệt của chủ repo vì CORS; giới hạn độ dài URL, và script `decodeURIComponent` lần thứ hai nên dữ liệu có `%` sẽ lỗi).
    - `doPost` chỉ hiểu body `{"transactions": [...]}`. Nó **xóa Sheet trước khi đọc body**, nên mọi body khác (ví dụ `{"action":"save","data":[...]}`) làm mất toàn bộ dữ liệu mà vẫn trả HTTP 200. Lỗi kiểu `{"status":"error","message":...}` cũng trả 200.
    - Chỉ 7 cột `id,date,type,source,category,amount,note`: không có `targetSource`, `updatedAt`, không đồng bộ danh mục/nguồn/số dư.
- `Code.gs` v2 **đã được chủ repo deploy trên Google thật (30/10/2026)** và điện thoại + máy tính đồng bộ được. Sự cố lúc deploy: một **New deployment** mặc định "Thực thi bằng: Người dùng truy cập" + "Chỉ mình tôi" làm trình duyệt báo `Failed to fetch` (Google trả trang đăng nhập không có CORS), trong khi điện thoại còn dùng URL deployment cũ nên vẫn "Đã lưu" — phải là **Tôi** + **Bất kỳ ai** và dán cùng URL cho mọi máy (README "Nâng cấp lên v2"). Vẫn chưa kiểm chứng cách POST `text/plain` đọc phản hồi trên mọi trình duyệt (v2 có dự phòng `GET ?action=sync&payload=` khi POST bị chặn).

## Cấu trúc

`index.html` nạp các script theo thứ tự (hàm/biến là global, không dùng module):
`version → utils → data → ui → categories → budgets → salary → recurring → debts → transactions → tags → import → sources → savings → charts → sync → backup → app → pwa`.
Chart.js, Font Awesome và pdf.js nằm trong `vendor/` (không dùng CDN; pdf.js **không** nằm trong `index.html` / `APP_SHELL`: `js/import.js` nạp nó lần đầu chọn file PDF, service worker cache sau đó). Mỗi file nội bộ `index.html` nạp phải có trong `APP_SHELL` của `sw.js` (có test kiểm tra).

## Mô hình dữ liệu (localStorage)

- `fm_transactions`: `{id, date YYYY-MM-DD, type income|expense|transfer, source, targetSource, category, amount, note, updatedAt}`. Id `TX_<ms>`.
- Dữ liệu "meta" khai báo trong `META_DEFS` (`js/data.js`), lưu bằng `saveMeta(key)` (ghi `localStorage`, đóng dấu `fm_meta_updated[key]`, gọi `queueMeta`): `categories` (`fm_categories`), `sources` (`fm_sources`), `initialBalances` (`fm_initial_balances`), `budgets` (`fm_budgets`), `savings` (`fm_savings`: `{enabled, day, from, book, mode 'percent'|'fixed', percent, amount, since, lastMonth}`), `salary` (`fm_salary`: `{amount, warnPercent, debtWarnPercent, cardWarnPercent, groups: [{id, name, percent, saving}], assign: {tênDanhMục: idNhóm}}`; `amount` 0 = chưa đặt; thiếu `groups` thì dùng mẫu 50/30/20), `recurring` (`fm_recurring`), `debts` (`fm_debts`). Mỗi loại có hàm `normalize*` thuần trong `js/utils.js` (trả `null` nếu dữ liệu không dùng được).
- Đồng bộ: `fm_script_url`, `fm_script_token`, `fm_sync_baseline`, `fm_sync_dirty`, `fm_pending_upserts`, `fm_deleted_ids`, `fm_pending_meta`, `fm_meta_updated`. Sau thay đổi cục bộ luôn gọi `queueUpsert/queueDelete/saveMeta` (đặt `updatedAt` mới cho giao dịch đã sửa) rồi `syncToGoogleSheet()`.

## Quy ước

- Khi sửa file bằng script (Python `str.replace`) luôn `assert` chuỗi tìm thấy: Prettier đổi bố cục code/bảng nên thay chuỗi có thể âm thầm không làm gì (đã từng khiến tab Vay Nợ không render và bỏ sót cập nhật tài liệu).
- **Phiên bản**: `js/version.js` (`APP_VERSION` = `YYYY.MM.DD-<7 ký tự hash>`, `APP_BUILD_HASH`), `version.json` và dòng `CACHE_VERSION` của `sw.js` do `npm run stamp` (`scripts/stamp-version.js`) tự ghi, **không sửa tay**. Hash tính trên nội dung mọi file trong `APP_SHELL` (trừ `js/version.js`); ngày chỉ đổi khi nội dung đổi. **Sau khi sửa bất kỳ file nào trong `APP_SHELL` (js, css, index.html, manifest, icon…) phải chạy `npm run stamp` rồi commit cả ba file**; `tests/unit/version.test.js` (chạy cả trên CI) đỏ nếu quên. Hai nhánh cùng sửa app thì khi gộp có xung đột ở ba file này: giải bằng cách chạy lại `npm run stamp`. Phiên bản hiện ở chân menu trái và Cài đặt → Phiên Bản Ứng Dụng; nút "Kiểm tra bản mới" đọc `version.json` (không bao giờ qua cache: `sw.js` bỏ qua nó và trang gọi `cache: 'no-store'`); mỗi bản mới là một service worker mới nên cache cũ bị xóa, `install` tải file bằng `cache: 'reload'` (bỏ qua cache HTTP của GitHub Pages) và khi nó tiếp quản trang đang mở thì hiện thanh "Tải lại" (`controllerchange`, chỉ khi trang đã có service worker lúc nạp). Thêm file vào `APP_SHELL` là đủ để nó nằm trong hash.
- Git: làm việc trên branch được giao và không tạo PR trùng khi branch đã có PR (cập nhật mô tả PR bằng `update_pull_request`); commit message viết bằng English, mỗi cột mốc một commit, chạy `npm test`, `npm run test:unit`, `npm run format:check` trước khi push.
- Prettier theo `.prettierrc.json` (4 space, single quote, `;`, trailing comma, width 100). Comment code bằng English, chuỗi giao diện bằng tiếng Việt.
- Không nội suy dữ liệu người dùng vào `innerHTML` mà không qua `escapeHtml`; không dùng `onclick="fn('${data}')"` — dùng `data-*` + event delegation.
- Ngày luôn là chuỗi `YYYY-MM-DD` theo giờ địa phương. Không dùng `toISOString().split('T')[0]` cho ngày hiển thị/nhập (UTC lệch ngày).
- Hiển thị ngày luôn qua `formatDateDisplay` (`dd/mm/yyyy`); dữ liệu lưu, `<input type="date">` và so sánh vẫn là ISO `YYYY-MM-DD`. Không tự ghép chuỗi ngày kiểu khác.
- Ô nhập tiền là `<input type="text" data-money="positive|signed">` (tự thêm dấu `.` hàng nghìn khi gõ, `initMoneyInputs` gắn ở `initializeApp`). Đọc/ghi bằng `readMoneyInput(id)` / `setMoneyInput(id, value)` (trong `js/ui.js`), không dùng `.value`/`valueAsNumber`; logic thuần nằm ở `formatMoneyDigits`, `parseMoneyText` (`js/utils.js`). Ô tiền mới phải thêm `data-money` và test trong `tests/e2e/money.spec.js`. **Số 0 đứng đầu**: gõ ở cuối ô thì bỏ ngay (`0` rồi `5` thành `5`), nhưng sửa ở đầu / giữa (xóa chữ số đầu của `20.000` còn `0.000`) thì **giữ** (`formatMoneyDigits(text, signed, {keepLeadingZeros})`, bật khi con trỏ chưa ở cuối) để gõ tiếp chữ số mới thành `50.000`; rời ô (`blur`) mới gọn lại (`0.000` → `0`). Bỏ số 0 ngay lúc xóa là lỗi chủ repo gặp 7/11/2026 (chọn giao dịch cài sẵn 20.000, xóa số 2 thì mất ba số 0). **Hỏi một số tiền bằng `askMoney({title, message, value, signed, allowEmpty, confirmLabel})` (`js/ui.js`, hộp `#moneyPromptModal`, trả `null` khi hủy, `NaN` khi để trống/chỉ có dấu trừ, `0` khi trống mà `allowEmpty`), không dùng `window.prompt()`**: prompt của trình duyệt không hiện dấu phân cách khi gõ (từng sót ở Sửa số dư, Khớp số dư, ngân sách danh mục, trả nợ). Hàm gọi nó phải `async`, và sau `await` phải lấy lại dữ liệu (đồng bộ có thể đã thay danh sách). `attachMoneyInput` đọc `dataset.money` ở mỗi lần gõ nên hộp này đổi được giữa `signed` và `positive`; sau khi lưu, focus quay về nút cùng `data-*` dù danh sách đã vẽ lại. Trong test, `promptValue` của `openApp` tự trả lời hộp này (ghi câu hỏi vào `state.confirms`; `window.__amountAnswer` đổi câu trả lời giữa chừng); hộp thật được test ở `tests/e2e/amount-dialog.spec.js`.
- Điều hướng trên điện thoại (≤768px): thanh dưới `.mobile-nav` có đúng 4 trang (`overview, transactions, sources, debts`) và nút thêm `.floating-add-btn` **nằm trong thanh, ở giữa** (nằm đúng giữa thứ tự Tab; nhô lên 14px, viền trắng 6px che đường viền trên của thanh nên thanh không được đặt `overflow` khác `visible`). - Chi tiêu trên lương (`js/salary.js`, logic thuần `normalizeSalaryPlan` / `salaryLevel` / `computeSalaryStatus` trong `js/utils.js`): chỉ tính giao dịch `expense` của tháng hiện tại; mức 0 = an toàn, 1 = từ mốc cảnh báo (mặc định 80% lương, chỉnh được 1-100), 2 = từ 100% lương. Phần trăm hiển thị làm tròn **xuống** (không hiện 80% khi chưa tới mốc). Lương cố định do người dùng nhập, không tự lấy từ giao dịch thu "Lương / Thưởng". Chia nhóm (`normalizeSalaryGroups`, `salaryGroupFor`, `computeSalaryAllocation`): nhóm chi có hạn mức = percent × lương, cùng thang mức 0/1/2 theo `warnPercent`; danh mục chi chưa gán (hoặc gán vào nhóm đã xóa) tính vào **nhóm chi đầu tiên**, `assign` chỉ lưu ngoại lệ; tối đa một nhóm `saving` và tối đa 8 nhóm. Nhóm tiết kiệm **không** ghi giao dịch riêng: tiết kiệm = lương − tổng chi tháng, đạt mục tiêu khi tổng chi ≤ lương − mục tiêu, mức 1 từ `warnPercent` của hạn mức chi đó, mức 2 khi hụt. Khi sửa DOM hộp thoại chia nhóm phải đi qua draft (`readAllocationDraft` → `renderAllocationForm`) để không mất dữ liệu đang gõ; thẻ Tổng quan bị vẽ lại sau khi lưu nên phải trả focus thủ công. **Dư nợ so với lương** (`computeDebtStatus` trong `js/utils.js`, `renderDebtVsSalary` trong `js/salary.js`, gọi từ `renderOverview`): thẻ Dư Nợ ở Tổng quan có thêm dòng `#lbl-debt-salary` "Bằng X% lương · cảnh báo từ 30%"; từ mốc `debtWarnPercent` (mặc định 30, chỉnh 1-100 ở hộp thoại lương) dòng đó tô đỏ kèm biểu tượng và chữ; làm tròn xuống, tính bằng số nguyên nên đúng mốc là cảnh báo; ẩn khi không có nợ, nhắc đặt lương khi chưa có lương; chưa có toast khi dư nợ vừa vượt mốc. **Dùng thẻ / trả sau trong tháng** (`computeCardSpend` / `computeCardSpendStatus` trong `js/utils.js`, `renderCardSpend` / `notifyCardSpend` trong `js/salary.js`): dòng thứ hai `#lbl-card-spend` của thẻ Dư Nợ cộng chi (`expense`) từ nguồn loại `credit` trong tháng + rút tiền mặt từ thẻ (chuyển tiền từ thẻ sang nguồn không phải thẻ); **không** trừ khi trả sao kê (chuyển tiền vào thẻ) nên không về 0 như dư nợ, đó là lý do nó tồn tại (chủ repo đã dùng ~90% lương bằng Spaylater + Mastercard trong một tháng). Mốc `cardWarnPercent` (mặc định 30) mức 1, từ 100% lương mức 2; toast chỉ khi thêm mới khoản chi làm vượt mức (như `notifySalary`, gọi từ `handleTransactionSubmit`). Nguồn loại `debt` (khoản nợ) không tính là thẻ. Script cũ (legacy) không đồng bộ meta nên lương chỉ nằm trên thiết bị; thêm loại meta mới chỉ cần khai báo trong `META_DEFS` + `META_ACCESSORS` (sao lưu và sync v2 tự chạy theo `META_DEFS`, `Code.gs` không cần đổi).

- **Thẻ (tag) của giao dịch** là các từ `#thẻ` nằm trong chính `note`, **không có trường riêng**: Sheet (script cũ lẫn v2), CSV, sao lưu, đồng bộ và tìm kiếm tự mang theo mà **không phải đổi `Code.gs`** (một trường `tags` riêng sẽ bị `Code.gs` bỏ rơi vì nó chỉ ghi các cột cố định, và thẻ mất sau lần đồng bộ). Thẻ = `#` + chữ cái + chữ / số / `_` / `-`, tối đa 30 ký tự, tối đa `MAX_TAGS` (10) mỗi giao dịch; `#12` hay `#thẻ,` dính dấu câu **không** phải thẻ; so sánh không phân biệt hoa thường và giữ cách viết đầu tiên (`tagKey`, `uniqueTags`). Hàm thuần trong `js/utils.js`: `extractTags` (tách ghi chú thành text + thẻ), `parseTagInput`, `composeNote` (text rồi các `#thẻ` ở cuối), `collectTags` (đếm, nhiều nhất trước), `filterTransactions({tag})`. Danh sách: chip `.tag-chip[data-action=tag]` cạnh ghi chú (`.note-cell`), chạm chip lọc theo thẻ (`filterByTag`, giữ các bộ lọc khác); bộ lọc `#filter-tag` chỉ hiện khi đã có thẻ, và dòng tóm tắt Thu / Chi / Chênh lệch khi lọc theo thẻ chính là lãi / lỗ của khách hay đơn hàng đó. `showTransactionsFor` nhận `tag`. Báo cáo theo thẻ ở trang Thẻ & Khách Hàng (`js/tags.js`; hàm thuần `computeTagReport`, `renameTagInNote`, `planTagRename` trong `js/utils.js`): thu / chi / lãi lỗ theo thẻ, giao dịch nhiều thẻ tính vào từng thẻ, chuyển tiền chỉ tính số giao dịch. **Đổi tên = viết lại `#thẻ` trong `note` của đúng các giao dịch có thẻ đó** (đóng dấu `updatedAt`, `queueUpsert` từng dòng, rồi `syncToGoogleSheet()`); đặt tên trùng một thẻ đang có thì **gộp** (dùng cách viết đang có; giao dịch mang cả hai thẻ chỉ còn một), chỉ đổi hoa / thường thì vẫn là đổi tên. - **Hạn thanh toán thẻ** (`computeCardDue` / `cardDueLevel` / `cardDuesToRemind` trong `js/utils.js`, `describeCardDue` / `remindCardDues` trong `js/sources.js`): nguồn loại `credit` có `dueDay` hiện dòng `Cần trả X trước dd/mm/yyyy (còn N ngày)` (đỏ kèm biểu tượng từ `CARD_DUE_WARN_DAYS` = 3 ngày trước hạn hoặc khi quá hạn). Có `statementDay` thì số phải trả = dư nợ lúc chốt sao kê gần nhất trừ khoản đã trả vào thẻ sau đó (chi sau ngày chốt thuộc kỳ sau) và hạn = ngày hạn đầu tiên sau kỳ chốt, nên sao kê chưa trả hiện _quá hạn_ chứ không nhảy sang tháng sau; không có `statementDay` thì là toàn bộ dư nợ và ngày hạn kế tiếp. Toast mỗi ngày một lần trên thiết bị (`fm_card_due_reminder_day`) và **chỉ sau khi đọc xong Sheet** (`syncFromGoogleSheet().then(remindCardDues)`; `handleReturnToApp` cũng đợi `refreshFromSheet()`) để khoản đã trả ở máy khác không bị báo là còn nợ — có test đỏ khi đảo thứ tự. **Ngày chốt sao kê là ngày CUỐI của kỳ** (VPBank: kỳ 21/09–20/10 thì chốt ngày **20**; giao dịch đến hết ngày chốt thuộc sao kê đó, từ hôm sau thuộc kỳ sau — chủ repo từng nhập 21 là lệch một ngày). Khi đã quá hạn, dòng "Hạn thanh toán ngày D" của thẻ chỉ ghi "hằng tháng" (không kèm "còn N ngày": đó là hạn của kỳ sau và đọc như mâu thuẫn với "quá hạn"). **Nút "Đã trả"** dưới dòng "Cần trả" (`data-action=pay-card` → `openCardPayModal` / `handleCardPaySubmit` / `cardPaySourceNames` trong `js/sources.js`, hộp `#cardPayModal`): số tiền điền sẵn bằng số phải trả (sửa được, trả ít hay nhiều hơn đều ghi), ngày mặc định hôm nay, chọn nguồn trả (nguồn đang dùng, **không** phải thẻ / khoản nợ / sổ tiết kiệm; nhớ ở `fm_card_pay_source`) và tạo giao dịch **`transfer`** id `TX_CARDPAY_<ms>` từ nguồn đó sang thẻ, danh mục `TRANSFER_CATEGORY`, ghi chú `Trả sao kê <thẻ>`, nên số dư hai nguồn và dòng "Cần trả" đổi theo và đi qua sync / CSV như mọi chuyển tiền. Không ghi được khi không có nguồn trả (báo), nguồn trả hay thẻ bị lưu trữ giữa chừng thì không ghi gì. Số dư thẻ là một con số chung: tiền trả **không** gắn với một kỳ, phần trả vượt sao kê tự trừ vào chi tiêu kỳ sau — nếu số dư ban đầu của thẻ thấp hơn thực tế thì số dư thẻ lệch đúng bằng phần chênh đó (sự cố 7/11/2026: số dư ban đầu −712.493 trong khi sao kê thật 1.695.414, trả 1.695.414 làm số dư thẻ chỉ còn −399.740 thay vì −1.382.661); sửa bằng Sửa số dư / Khớp số dư, không phải bằng giao dịch.
- **Mốc sao kê và kỳ sao kê của thẻ** (`js/sources.js`, `js/transactions.js`; hàm thuần `normalizeLastStatement`, `latestStatementDate`, `statementCycles`, `computeCardCycleTotals` trong `js/utils.js`). **Dư nợ cuối kỳ của sao kê gần nhất** là `source.lastStatement = {date, balance}` (chỉ thẻ `credit`, không có thuộc tính khi trống; ô `#srcStatementBalance` trong Sửa nguồn; `date` = ngày chốt gần nhất lúc nhập, giữ nguyên nếu lưu lại cùng số và cùng ngày chốt; cần có ngày chốt). `computeCardDue` có mốc thì số nợ lúc chốt = `balance` ± các giao dịch giữa ngày mốc và ngày chốt, **không dùng số dư ban đầu**; mốc mới hơn ngày chốt gần nhất (gõ sai ngày) bị bỏ qua. Nút **Xem theo kỳ** trên thẻ có ngày chốt = `showTransactionsFor({source, cycle: 'closed'})` (kỳ gần nhất đã chốt; `'current'` là kỳ đang mở).
- **Trả nợ ghi giao dịch** (`js/debts.js`): `openDebtPayModal` / `handleDebtPaySubmit`. ## Quyết định thiết kế đã chốt (đừng đảo ngược khi chưa hỏi)

- "Tổng số dư khả dụng" = tổng số dư các nguồn **không phải nợ và không phải sổ tiết kiệm** (kể cả số dư ban đầu; sổ tiết kiệm là loại `savings`, `SOURCE_KINDS.savings.saving`, có thẻ "Tổng tiết kiệm" riêng — chủ repo muốn tiền gửi sổ được "trừ" khỏi số dư). Nguồn nợ = nguồn có loại `credit` (thẻ tín dụng/trả sau) hoặc `debt` (khoản nợ), định nghĩa ở `SOURCE_KINDS` trong `js/utils.js`; mặc định `Thẻ Tín Dụng`, `Spaylater` là `credit`, `Nợ Công Ty` là `debt` (nếu "Nợ Công Ty" thực ra là công ty nợ chủ repo thì đổi loại sang `other`). "Dư nợ" = tổng phần âm của các nguồn nợ. Số dư **ban đầu dương** của một nguồn nợ (`fm_initial_balances`, nhập ở "Sửa số dư") bù vào các khoản chi nên dư nợ có thể bằng 0 dù đã chi qua thẻ (sự cố 30/10/2026: Spaylater chi 464.140 đ mà Dư nợ hiện 0 đ); thẻ nguồn luôn hiện dòng "Số dư ban đầu" khi khác 0, nguồn nợ có số dư ban đầu dương hiện thêm cảnh báo `.source-warn`, và hộp nhập số dư của nguồn nợ gợi ý nhập 0 hoặc số âm (`describeOpening`, `editInitialBalance` trong `js/sources.js`). Nút **Khớp số dư** (`matchSourceBalance`, logic thuần `openingBalanceToMatch` / `balanceFromAvailable` trong `js/utils.js`) nhập số thực tế rồi đặt lại số dư **ban đầu** = số thực tế − tổng các giao dịch, nên không đụng giao dịch nào; thẻ tín dụng có hạn mức thì hỏi số **khả dụng** (số dư = khả dụng − hạn mức). Số dư ban đầu của SPayLater của chủ repo cần khớp với ứng dụng Shopee (hạn mức 30.000.000, ngày chốt 24, hạn trả mùng 10 tháng sau).
- Card "Thu/Chi tháng này" chỉ cộng tháng hiện tại; biểu đồ tròn = chi tháng này; biểu đồ cột = 6 tháng gần nhất.
- Sync (xem comment đầu `js/sync.js`): **không bao giờ ghi lên server trước khi đã đọc và nhận diện được giao thức** (`GET ?v=2`: mảng = `legacy`, `{version: 2}` = `v2`).
    - `legacy` (script thật hiện tại của chủ repo): ghi bằng đúng `{"transactions": [...]}` (POST `text/plain`, không preflight); nếu không gửi được thì dự phòng `GET ?action=save&data=` khi URL ≤ 6000 ký tự và không có `%`, ngược lại không gửi gì và báo lỗi. `targetSource` đi trong cột category (`Chuyển tiền nội bộ → <nguồn nhận>`). Chỉ đồng bộ giao dịch; thay đổi danh mục/meta không kích hoạt ghi. Có test hồi quy `mọi lần ghi ... đều là {transactions}`.
    - `v2` (`apps-script/Code.gs`, đã deploy): POST `{action:'sync', token, replace, upserts, deletes, meta}`; server áp dụng theo `updatedAt` (bản mới hơn hoặc bằng thắng) và trả lại **toàn bộ trạng thái**, client gộp lại (`reconcileV2`). Meta (`categories, sources, initialBalances, budgets, salary, savings, recurring, debts`) đồng bộ nguyên khối theo `fm_meta_updated[key]`; lần đầu kết nối thì gộp hai phía (`mergeMetaFirstContact`). Token = Script Property `FM_TOKEN`, chủ repo nhập ở Cài đặt (`fm_script_token`, không nằm trong backup). `Code.gs` luôn validate trước khi ghi và vẫn hiểu các yêu cầu của script cũ (superset).
    - Mọi chỗ gọi `saveMeta` do người dùng thao tác **phải** gọi `syncToGoogleSheet()` ngay sau đó: `saveMeta` chỉ xếp hàng (`queueMeta`), không tự đẩy. Sự cố 30/10/2026: `editInitialBalance`, `matchSourceBalance`, `archiveSource`, `deleteSource` thiếu lời gọi này nên số dư ban đầu (Dư nợ) từ điện thoại không lên Sheet cho tới lần đồng bộ sau; có test `sync-v2.spec.js` (nhóm "Số dư ban đầu và quay lại cửa sổ").
    - App chỉ đọc Sheet lúc mở; thêm `refreshFromSheet` (`js/sync.js`, gắn ở `initializeApp` vào `focus` và `visibilitychange`): quay lại cửa sổ / tab thì đọc lại **không hiện "Đang tải..."** (`syncFromGoogleSheet({quiet:true})`), tối đa 30 giây một lần (`REFRESH_MIN_INTERVAL_MS`, `lastPullAt`), bỏ qua khi đang đẩy / chưa có URL / chưa đọc xong lần đầu. Cửa sổ PWA mở cả ngày trên máy tính nhờ đó nhận thay đổi từ điện thoại.
    - Khôi phục sao lưu (`importBackup` trong `js/backup.js`) **giữ nguyên URL Web App đang dùng của máy** (`targetUrl = webAppUrl || backup.data.scriptUrl`): chỉ máy chưa có URL mới lấy URL trong file. URL là cấu hình của máy, không phải dữ liệu: bản cũ để file sao lưu kéo máy về URL cũ nên dữ liệu bị đẩy lên deployment cũ (script cũ, không có meta) thay vì deployment v2 (sự cố 30/10/2026: điện thoại vẫn dùng URL deployment cũ nên chưa bao giờ đẩy được nguồn tiền / số dư lên Sheet v2).
    - Hàng chờ cục bộ: `fm_sync_dirty` (`merge|replace`), `fm_pending_upserts`, `fm_deleted_ids`, `fm_pending_meta`; xóa khi server xác nhận _trừ_ phần thay đổi sau khi request được dựng. Sheet trống không xóa dữ liệu máy; khôi phục backup/reset là `replace` (server thay hẳn kể cả meta).
    - Bài học (sự cố 28/10/2026): bản đầu của PR #3 gửi `{"action":"save","data":...}` — do giả định giao thức khi chưa thấy script thật — sẽ xóa Sheet. Luôn kiểm chứng giao thức với script thật trong sandbox trước khi đổi cách ghi.
